> **Статус: L1 и L2 сделаны (01.09.2026). L3 не начат.**

> | | косинус |
> |---|---|

> | один вопрос, один язык, разные слова | 0.701 – 0.937 |

> **сопоставление никогда не пересекает языки** (это не настройка), а порог —
> **0.85**, выше всех наблюдённых «разных вопросов». Около половины перефразов

> вопрос, которого не задавали.
>
> **Где брать эмбеддинги — план был прав, но по другой причине:** ключ Gemini
> и правда живёт только у агента, и вдобавок у OpenRouter, через который
> теперь идёт чат, эмбеддингов нет вообще. Добавлен кадр `embed` и

> за вопрос.
>
> **Попутно найдены и починены два живых бага определения языка:** «X деген не»
> отвечалось по-русски, английский вопрос — по-казахски.
>
> Живой замер: 0.8 с на семантическое попадание против 89 с на генерацию.

| Уровень | Как ищем | Стоимость | Ожидаемый вклад |
|---|---|---|---|
| **L1 — точное совпадение** | sha256 от нормализованного вопроса + язык + версия пайплайна | ~1 мс, 0 токенов | 30–40 % повторов |
| **L2 — семантическое** | эмбеддинг вопроса, косинус ≥ 0.92 к известным | ~100 мс, доли цента | +20–25 % |
| **L3 — канонический топик** | дешёвая flash-модель приводит вопрос к `topic_id` из каталога | ~1 с, копейки | +10–15 % |

**Нормализация для L1** (`backend/app/services/cache_service.py`):
lowercase → NFKC → убрать эмодзи и пунктуацию → схлопнуть пробелы → убрать вводные
(«объясни», «расскажи», «что такое», «түсіндір», «explain»). Порядок слов сохраняем
— он значим. Ключ: `sha256(f"{norm}|{lang}|{pipeline_version}")`.

**L2 — хранилище векторов:** пока записей < 50 000, держать векторы в Mongo и считать
косинус в памяти через numpy — это единицы миллисекунд. Дальше — Atlas Vector Search
или отдельный Qdrant. Начинать с векторной БД преждевременно.

**Где взять эмбеддинги:** ключ Gemini живёт только в контейнере агента, у бэкенда его
нет. Не размазывать ключ по двум сервисам — добавить агенту новый тип WS-запроса
`{"type":"embed","text":...}` рядом с существующим потоком. Бэкенд спрашивает вектор
у агента, ключ остаётся в одном месте.

## C2. Политика допуска — чтобы диск не забивался

Главный принцип: **счётчики дешёвые, видео дорогое**. Считаем все вопросы, храним
только горячие.

```
Запрос → нормализация → инкремент счётчика в question_stats (десятки байт)
      → hits == 1..2   → рендерим, кладём видео как EPHEMERAL (TTL 48 ч)
      → hits >= 3      → промоушен: видео становится WARM (TTL 30 дней,
                          продлевается при каждом попадании)
      → ручное одобрение → CURATED (без TTL, никогда не вытесняется)
```

**Три класса хранения:**

| Класс | TTL | Кто попадает | Вытеснение |
|---|---|---|---|
| `ephemeral` | 48 ч | любой сгенерированный ответ | первым, по LRU |
| `warm` | 30 дней, продлевается | ≥ 3 обращений за 30 дней | по score |
| `curated` | ∞ | ручное одобрение + сид-библиотека (C6) | никогда |

**Бюджет диска.** Переменная `MEDIA_MAX_BYTES`. **Решение владельца (31.08.2026):
старт 20 ГБ, потолок 30 ГБ**; при заметных просадках hit-rate или частых вытеснениях
warm — поднимаем, это не проблема. Значит, порог вытеснения считаем от текущего
`MEDIA_MAX_BYTES`, а не от захардкоженного числа, и в метрики (C8) обязательно
выводим «сколько раз за сутки сработало вытеснение» — это и есть сигнал «пора
увеличивать».

Фоновая задача `scripts/gc_media.py` раз в час:

1. Считает занятый объём.
2. Если > 90 % бюджета — вытесняет по возрастанию
   `score = hits × exp(-дней_с_последнего_обращения / 14) / размер_МБ`.
3. `curated` не трогает никогда; при исчерпании ephemeral + warm — алерт, а не
   удаление curated.

**Дедупликация.** sha256 содержимого mp4: если два вопроса дали байт-в-байт одинаковый
файл, хранится один, у записей — ref-count (коллекция `media_files`).

**Что НЕ кэшируем** (иначе кэш сам станет свалкой):

- запросы со скриншотами — они уникальны по определению;
- вопросы длиннее 200 символов — это уже персональная задача, а не «частый вопрос»;
- вопросы, где сработала эвристика на персональные данные (имена, номера,
  «моя контрольная»);
- всё, что упало на рендере (`render_error != ""`);
- случаи `is_science == false`.

анимациями, качество которых не зависит от настроения LLM.

**Чем curated отличается от автокэша** (разница принципиальная):

| | Автокэш (`ephemeral` / `warm`) | Curated |
|---|---|---|
| Кто одобрил | никто, это сырой вывод LLM | человек посмотрел и принял |
| Качество | как повезёт: формула может быть кривой, казахский — машинным | гарантировано |
| Скрипт | живёт в БД, перегенерируется | заморожен в `content/`, в git |
| Удаляется | да, по TTL и вытеснению | никогда |
| При смене `pipeline_version` | пропадает | перерендеривается тем же скриптом |

**Решения владельца (31.08.2026):** проверяет владелец продукта лично;
**языки — все три сразу (kk, ru, en)**, поскольку на старте тем в библиотеке
немного и общий объём проверки остаётся посильным.

⚠️ **Ограничитель — не диск, а часы проверяющего.** Поэтому растём волнами:

1. **Волна 1:** 25–30 тем × 3 языка = 75–90 роликов — это ~1.5 рабочих дня проверки.
   Берём самые очевидные темы школьной программы.
2. **Волна 2 и далее:** расширяем **только по статистике** `question_stats` — что
   реально спрашивают. Не проверять вслепую то, что никто не спросит.
3. Интерфейс проверки: простая админ-страница «одобрить / отклонить / перегенерировать»
   со списком кандидатов, отсортированных по числу обращений. Без неё проверка сотни
   роликов превращается в ручное ковыряние в файлах.

### Один скрипт на три языка — экономит две трети работы

Поскольку языков сразу три, ключевое проектное решение: **не держать три отдельных
manim-скрипта на тему.** Анимация (что и куда летит, какие оси, какие стрелки) от
языка не зависит — меняются только надписи. Поэтому:

- анимация описывается **одним** скриптом, все строки вынесены в ключи:
  `Text(S["title"])` вместо `Text("Что такое гравитация")`;
- переводы лежат рядом в `strings.{kk,ru,en}.yaml`;
- `seed_library.py` рендерит один скрипт три раза, подставляя нужный словарь.

Что это даёт при проверке: **анимацию смотришь один раз**, дальше по каждому языку
только вычитываешь текст — это минуты, а не полный просмотр. Фактическая
трудоёмкость трёх языков получается ближе к 1.4×, а не к 3×. Плюс правка анимации
автоматически прилетает во все языки, а не требует трёх одинаковых правок.

Отдельный скрипт для конкретного языка допустим как исключение — если разбор
принципиально другой (например, другая система обозначений).

```yaml
# content/curated/physics/gravity_basics/topic.yaml
topic_id: physics.gravity_basics
subject: physics
grade_range: [7, 9]
languages: [kk, ru, en]

aliases:                     # синонимы вопроса для L1/L2-поиска
  kk: ["гравитация деген не", "ауырлық күші"]
  ru: ["что такое гравитация", "объясни гравитацию", "сила тяжести"]
  en: ["what is gravity", "explain gravity"]

# ОДИН скрипт на все языки; строки берутся из strings.<lang>.yaml
manim_script: scene.py       # зафиксирован, проверен человеком
strings: strings.{lang}.yaml
educator_text: text.{lang}.md

review:                      # проверка ведётся по языкам отдельно
  animation: { by: "owner", at: "2026-09-01", approved: true }
  kk: { approved: true,  at: "2026-09-01" }
  ru: { approved: true,  at: "2026-09-01" }
  en: { approved: false }    # ролик не публикуется, пока не одобрен
```


3. `scripts/seed_library.py` — рендерит каждый одобренный язык в высоком качестве

4. Прогонять в CI при смене `pipeline_version`.

**Оценка объёма** (три языка, с учётом общего скрипта — анимация проверяется один

## D1. Почему не работает ползунок перемотки — четыре независимые причины  ✅ СДЕЛАНО

**D1.1 — `isSeeking` залипает.** `VideoPanel.tsx:341-352`: конец перемотки ловится
через `onMouseUp` / `onTouchEnd` **на самом `<input type="range">`**. Если отпустить
кнопку мыши, уведя курсор за пределы ползунка (а при перетаскивании это происходит
постоянно), событие не приходит → `isSeeking` навсегда остаётся `true` →
`handleTimeUpdate` (`VideoPanel.tsx:209-213`) перестаёт обновлять `currentTime` →
ползунок замирает, хотя видео играет. **Это основная причина.**

**D1.2 — клавиатура ломает то же самое.** Стрелки на сфокусированном range меняют
значение без `mousedown` / `mouseup` — флаг `isSeeking` не выставляется и не снимается.

**D1.3 — `duration` может быть `NaN`.** `max={duration || 0}` и
`(currentTime / duration) * 100` (`VideoPanel.tsx:568`) дают `NaN` в CSS-градиенте,
пока метаданные не загружены — ползунок выглядит мёртвым.

**D1.4 — сервер не отдавал HTTP Range. ✅ ПОДТВЕРЖДЕНО ИЗМЕРЕНИЕМ.**
`pip show starlette` в контейнере → **0.36.3** (Range появился в 0.37.0).
Запрос `Range: bytes=0-100` к ролику 784340 Б → `200 OK`, весь файл, без
`Accept-Ranges`. Разбор атомов реального mp4 → `ftyp/free/mdat/moov`, `moov`
на **99% файла**, то есть `+faststart` не применялся.
Исправлено: Range реализован в эндпоинте (+ ETag, If-Range, 416), рендеры
ремуксятся через `-c copy -movflags +faststart`. После правки
`bytes=700000-` отдаёт 84 КБ вместо 784 КБ.

Исходные гипотезы (обе оказались верны):

- `FileResponse` в Starlette получил поддержку `Range` только в 0.37.0, а
  `fastapi==0.109.2` тянет `starlette < 0.37`. Проверить:
  ```bash
  docker compose exec backend pip show starlette
  ```
  Если версия < 0.37 — перемотка вперёд физически невозможна: браузер не может
  запросить кусок файла. Лечится обновлением FastAPI/Starlette либо ручной
  реализацией `Range` в `/media` (`backend/main.py:707`).
- Манимовский mp4 пишется **без `+faststart`** — атом `moov` в конце файла, браузер
  не может перематывать, пока не скачает ролик целиком.

Проверка обеих гипотез одной командой:
```bash
curl -s -D- -o /dev/null -H 'Range: bytes=0-100' -b cookies.txt http://localhost:3000/media/X.mp4
```
Нужно увидеть `206 Partial Content` и `Accept-Ranges: bytes`. Если пришёл `200` —
причина найдена.

**Что делать:**

1. Заменить `<input type="range">` на собственный `ProgressBar` на **pointer events**
   с `setPointerCapture` — курсор больше не сможет «убежать» из-под контрола; плюс
   обработчики `pointercancel` и `window.pointerup` как страховка.
2. Синхронизироваться по нативным событиям видео `seeking` / `seeked`, а не по
   своему флагу.
3. Гейт `Number.isFinite(duration) && duration > 0` перед любыми расчётами процентов.
4. Опираться на `video.seekable` (куда реально можно прыгнуть) и рисовать
   `video.buffered` полосой загрузки.
5. Сервер: включить Range + `Accept-Ranges` + `ETag` +
   `Cache-Control: private, max-age=604800`; в nginx для `/media` — `proxy_buffering off`.
6. Постобработка ffmpeg после рендера: `-movflags +faststart -g 30` — moov в начало,
   ключевой кадр раз в 2 с, отсюда точная перемотка.

## D2. Почему «кисть сама включается»  ✅ СДЕЛАНО

`VideoPanel.tsx:471-474`: canvas получает `pointer-events-auto` **всегда, когда
`isPaused === true`**. Отсюда три следствия:

- пользователь ставит паузу → верхний слой перехватывает мышь → клик по видео
  **рисует красную линию** вместо возобновления воспроизведения;
- `onClick={togglePlayPause}` на `<video>` (`VideoPanel.tsx:466`) физически
  недостижим — он под canvas;
- `handleSeekStart` (`VideoPanel.tsx:335`) сам ставит паузу при перемотке, поэтому
  достаточно тронуть ползунок, чтобы включилось рисование.

**Что делать:**

1. Режим рисования — **явный тумблер** (кнопка на панели + клавиша `D`), по умолчанию
   **выключен**. Пауза и режим рисования — разные вещи.
2. `pointer-events` на canvas только при `drawMode === true`.
3. Курсор-подсказка и рамка вокруг видео, когда режим включён — чтобы состояние
   было видно.
4. При включении рисования — автопауза (это удобно), но не наоборот.

## E1. Новый сервис `exporter`

Отдельный контейнер, а не внутри существующих:

- в **агенте** read-only rootfs и лимиты под манимом — тяжёлый ffmpeg туда не влезет;
- в **бэкенде** ffmpeg заблокирует event loop.

```
exporter/
├── Dockerfile          # python:3.12-slim + ffmpeg + libreoffice (опц., для pptx→pdf)
└── app/
    ├── worker.py       # берёт задачи из очереди
    ├── jobs/
    │   ├── gif.py      # фрагмент → GIF / WebM / APNG
    │   ├── clip.py     # фрагмент → mp4
    │   ├── frame.py    # кадр + аннотации → PNG
    │   ├── pptx.py     # презентация для учителя
    │   └── pdf.py      # раздатка / конспект
    └── storage.py      # результаты в exports/, TTL 24 ч
```

Очередь: на старте — коллекция Mongo `export_jobs` со статусами
(`queued → running → done | failed`) и воркер-пуллер. Redis/RQ — когда появится
второй воркер, не раньше.

**API:**

```
POST /api/export            {type, message_id, params}  → 202 {job_id}
GET  /api/export/{job_id}                               → {status, progress, url?}
WS   export_progress                                     → живой прогресс в UI
GET  /api/export/{job_id}/download                      → файл, Content-Disposition
```

Ограничения: 5 задач в час на пользователя, только свои сообщения, TTL результата 24 ч.

## E3. GIF из выбранного фрагмента — как просили

**Решение владельца (31.08.2026): делаем оба формата — GIF и mp4-клип.** По умолчанию
предвыбран mp4 (он в 10–20 раз меньше при лучшем качестве), но **GIF всегда на виду**
— это равноправная кнопка рядом, а не спрятанный в подменю «расширенный вариант».
Пользователь видит оба и выбирает сам.

**UI:** в плеере кнопка «Вырезать фрагмент» → на таймлайне появляется двойной ползунок
`[начало … конец]`, панель параметров и живое превью первого кадра. Переключатель
формата — два видимых чипа: `MP4` (выбран) и `GIF`, с подписью веса под каждым
(«~1.2 МБ» / «~8 МБ»), пересчитывается при смене длины и ширины. Так выбор в пользу
mp4 происходит сам собой, но без принуждения.

Параметры: fps (10/15/20), ширина (320/480/640/800), зацикливание, включать ли
аннотации, подпись снизу (вопрос или название темы). Для mp4 те же параметры, кроме
палитры.

**Пайплайн (ffmpeg, двухпроходная палитра — иначе GIF будет грязным):**

```bash
ffmpeg -ss <start> -to <end> -i in.mp4 \
  -vf "fps=15,scale=640:-1:flags=lanczos,split[a][b];[a]palettegen=max_colors=128[p];[b][p]paletteuse=dither=bayer" \
  -loop 0 out.gif
```

**Ограничения (иначе получим 80-мегабайтные GIF):**

- длительность фрагмента ≤ 15 с;
- итоговый размер ≤ 20 МБ; при превышении автоматически понижать fps/ширину и
  пересобирать (до двух попыток);
- если и так не влезает — предложить **WebM/mp4-клип** (в 10–20 раз меньше при том же
  качестве) или **APNG**.

**Почему серверно, а не в браузере:** ffmpeg.wasm весит ~25 МБ, съедает 1–2 ГБ RAM на
кодировании и не тянет на школьных ноутбуках; видео и так уже лежит на сервере.

## F6. Доступ только после авторизации + защита от перегрузки

> **Статус: сделано (01.09.2026).** Блокер публичного запуска снят.
>
> | Мера | В плане | Поставлено |
> |---|---|---|
> | Одновременных на юзера | 1 | **1** |
> | Генераций в час | 5 | **15** |
> | Генераций в сутки | 20 | **50** |
> | Регистраций с IP/час | 3 | **100** |
> | Потолок очереди | N | **20** |
>
> **Почему цифры выше плановых.** Настоящий ограничитель — единственный агент:
> генерация занимает его ~90 секунд, то есть система физически не выдаёт
> больше ~40 роликов в час. Поэтому защищает не «сколько в час», а
> «одновременно = 1»; часовой и суточный лимиты — это потолки для спокойствия,
> и они могут быть щедрыми.
>
> Регистрации: 3 с IP заблокировали бы школьный класс за одним NAT. Лимит
> регистраций к тому же не ограничивает расходы — их ограничивает квота на
> пользователя, а за ней агент.
>
> **Кэш квоту не тратит, неудачная генерация возвращается** (при ошибке агента,
> при его отключении и при подметании зависших запросов). 22 теста.
>
> **Осталось из таблицы:** `limit_req_zone` в nginx и подтверждение e-mail —
> оба нужны, только если пойдут злоупотребления.

**Решение владельца (31.08.2026): сервис целиком закрыт авторизацией**, включая
curated-библиотеку. Публичного просмотра роликов без входа не будет. Мотив —
не допустить DDoS и злоупотреблений.

Здесь важная поправка: **авторизация сама по себе от перегрузки не защищает.**
Регистрация открыта, аккаунтов можно наделать сколько угодно, а генерация видео —
самая дорогая операция в системе. Сейчас в коде:

- рейт-лимитер стоит **только на логине** (`LoginLimiter`, `main.py:241`) —
  5 попыток за 15 минут;
- на `signup` лимита нет вообще;
- на `user_message` (то есть на запуск генерации видео) **нет никаких квот**
  (`main.py:877`) — один залогиненный пользователь может поставить в очередь
  неограниченное число рендеров и занять единственного агента насовсем.

**Что добавить, чтобы решение «только по логину» реально работало:**

| Мера | Где | Значение на старте |
|---|---|---|
| Квота на генерацию | `ws/ui.py`, до `send_to_agent` | 20 видео в сутки и 5 в час на пользователя |
| Одновременных запросов на пользователя | `ws/ui.py` | 1 (второй — в очередь, с сообщением «дождитесь текущего») |
| Рейт-лимит на `signup` | `api/auth.py` | 3 регистрации в час с одного IP |
| Рейт-лимит на экспорт | `api/export.py` | 5 задач в час (уже заложено в E1) |
| Глобальный потолок очереди | `ws/manager.py` | N запросов, дальше — честное «сервис перегружен» |
| Лимиты на уровне nginx | `nginx.conf.template` | `limit_req_zone` на `/api/auth/*` и `/ws` |
| Подтверждение e-mail | `api/auth.py` | опционально, если пойдут фейковые регистрации |

Хорошая новость: **кэш из Фазы C — сам по себе лучшая защита от нагрузки.** Попадание
в кэш стоит ~1 мс вместо нескольких минут рендера, поэтому чем выше hit-rate, тем
меньше поводов для перегрузки в принципе. Квоты имеет смысл считать только по
промахам кэша — ответы из библиотеки квоту тратить не должны.

### Что решать по ходу дела (не блокирует старт)

- **Порог семантического совпадения** (C1, сейчас 0.92) — настраивается только на
  живых данных: слишком низкий начнёт подсовывать чужие ответы, слишком высокий
  убьёт пользу L2. Первые две недели логировать все околопороговые случаи и смотреть
  глазами.
- **Порог промоушена в warm** (C2, сейчас 3 обращения) — зависит от реального
  трафика. При малом потоке имеет смысл снизить до 2.
- **Качество рендера для автокэша** (D3.12) — 720p30 против 1080p60: втрое разница
  в объёме и времени рендера. Решать, когда увидим реальный поток.
- **Список тем волны 1** — составить перед стартом Фазы C.
